# 踩坑记录

按类别整理，全部来自真实调试现场。每条都写明**现象 → 原因 → 修法**。
配置阶段的操作步骤见 [SETUP.md](SETUP.md)。

---

## A. 速度：看起来一样，其实慢十倍

### A1. 显存不够不会报错，只会把一方悄悄挪到 CPU

**现象**：同样参数，出图有时 27 秒，有时 90 秒；翻译 5 秒变 2 分钟。

**原因**：8 GB 显存里同时放 5.1 GB 翻译模型和 3 GB 出图模型装不下，驱动把其中一方挪到内存，速度掉一个数量级，**但没有任何报错**。

**判断**：`nvidia-smi --query-gpu=utilization.gpu` 利用率 90% 以上还慢，就是有层在 CPU。

**修法**：出图前卸翻译模型；翻译前让 ComfyUI 释放。实测 90 秒 → 27 秒。

### A2. `size_vram > 0` 不代表模型在显存里

**现象**：日志显示"模型已在显存"，但翻译依旧 100 秒。

**原因**：Ollama `/api/ps` 的 `size_vram` 只要大于 0 就说明**有一部分**在显存，半驻留等于一半在跑 CPU。

**修法**：

```python
fully = total > 0 and vram >= total * 0.9
```

而且**半驻留的模型不会自己搬回显存**，必须 `keep_alive=0` 卸载后重新加载。

### A3. 上下文越长，生成越慢（最反直觉）

实测同一模型、同一张显卡：

| prompt token | 生成速度 |
|---|---|
| 29 | 18.5 tok/s |
| 378 | 12.8 tok/s |
| 1086 | 8.8 tok/s |
| 2148 | 6.0 tok/s |

**结论**："多写规则让它更听话"是有代价的。规则文件从 1500 字堆到 6600 字，每次翻译多花约 25 秒。

### A4. 二次请求是隐形时间黑洞

**现象**：`总 108 秒 = 首轮 28 秒 + 补全 80 秒`。

**原因**：词表不够时"补一轮"，如果照搬完整规则 + 首轮输出重发，等于把最慢的活再干一遍。

**修法**：补全请求要极简，只发必要上下文；或者干脆关掉补全（宁可词表少几条）。

### A5. Ollama 的模型摆放会"半速"，重载一次能恢复

**现象**：同一模型，有时 50 tok/s，有时 5 tok/s，显存占用看起来一样。

**修法**：翻译前跑一个 8 token 的探针测速，低于 12 tok/s 就卸载重载一次再测。

### A6. ComfyUI 队列里有残留任务时，GPU 一直被占

**现象**：什么都没跑，翻译却要 340 秒。

**原因**：`/queue` 里 `queue_running` 非空，模型不释放，GPU 算力被吃掉。

**修法**：`POST /interrupt` + `POST /queue {"clear": true}`。**实测有卡死的任务 `/interrupt` 也停不掉，只能重启 ComfyUI 进程。**

### A7. `/free` 是异步的，调用完立刻用会踩空

`POST /free` 返回 200 时显存还没退。要轮询 `nvidia-smi` 等到稳定（1~3 秒）再加载别的模型。

## B. 模型与文件

### B1. 模型下载断流会留下"看起来正常"的残缺文件

**现象**：`PytorchStreamReader failed reading zip archive: failed finding central directory`。

**原因**：`codeformer-v0.1.0.pth` 只有 11 MB（正常 359 MB），下载中途断了。

**修法**：下完**核对大小**；用支持续传的镜像：

```powershell
curl.exe -L --retry 5 -C - -o "模型路径" "https://ghfast.top/https://github.com/..."
```

实测速度：ghfast.top 1.8 MB/s ｜ gh-proxy.com 0.3 MB/s ｜ GitHub 直连 0.05 MB/s。

### B2. 清模型文件前必须 grep 代码里的硬编码文件名

**现象**：按"工作流没引用"清掉一个特征迁移模型，映射页立刻报错。

**原因**：工作流 JSON 只列了一部分模型，代码里还写着：

```python
"swap_model": "inswapper_ff.onnx"
```

**修法**：清理前 `grep -r "\.onnx\|\.pth\|\.safetensors"`，工作流和代码两边都要查。

### B3. 模型名是枚举，改一边没用

**现象**：出图报 `{"type":"value_not_in_list"}`，节点名是 `ReActorFaceSwap`。

**原因**：`swap_model` 只能取枚举里的值，代码与工作流任一处写错就整体失败。

### B4. 模型文件缺失不会提前警告

ReActor 首次运行会自动下载 6 个模型，国内经常超时失败，表现却是"出图直接报错"。装完节点后先手动补齐模型再跑。

## C. 出图与参数

### C1. ComfyUI 不接受负数种子

```
seed = -123  →  prompt_outputs_failed_validation
```

有效范围 `0 ~ 2147483647`，传入前 `max(0, seed)`。界面上填负数会被静默纠正为 0。

### C2. 同种子 + 同参数 = 命中缓存，3 秒返回同一张

不是 bug。要么换种子，要么改任意一个参数。日志会提示"种子固定 N：同参数重复跑会直接返回缓存"。

### C3. 倍率低于 1.5 观感发软

第二遍重绘被放弃，等于只出草图。实测 1.0 明显比 1.5 糊。

### C4. 画布调大 ≠ 更清晰

```
512×768 ×1.5  →  成品 768×1152  →  27 秒   ✅
768×1024 ×1.1  →  成品 768×1152  →  65 秒   ❌ 更慢更糊
```

看的是"倍率是否够 1.5"，不是"画布多大"。

### C5. 修复模型之间差异极小

同一张图实测：

```
源图             清晰度 117.2
GFPGAN           113.1 ｜ 相似度 0.662
CodeFormer 0.5   112.7 ｜ 相似度 0.660
不用修复          114.4 ｜ 相似度 0.687   ← 反而最好
```

**结论**：别为修图模型纠结，脸本来就小的时候越修越不像。

### C6. 映射强度调来调去，结果几乎不变

0.3 与 0.5、换修复模型，清晰度和相似度差异都在 ±2 以内。**这个模块的天花板在算法本身，不在参数。**

### C7. LoRA / FaceID 权重过高会僵

LoRA 0.6 + FaceID 0.8 出图"证件照感"重；0.5 / 0.65 更自然。修复强度 0.75 磨皮明显，写实场景建议 0.35~0.5。


### C8. 相似度是这个项目唯一可量化的验收指标

调参时不要靠"看着还行"，用相似度对比：

```
映射前 0.11 → 映射后 0.78   ✅ 生效
源图侧脸，映射前后 0.52 → 0.54  ❌ 无效，问题在构图不在参数
```

母版自映射会掉到 0.91 左右（二次压缩所致），可作为上限参考。

## D. 界面与 Tkinter

### D1. 线程里读 Tk 变量会静默失败

**现象**：日志永远跑到错误的页签；卸载提示看不见。

**原因**：工作线程 `self.some_var.get()` 抛异常被 `except` 吞掉，回落成默认值。

**修法**：主线程把需要的值打包进 `args` 字典，线程只读字典。

### D2. `Treeview` 做不出可换行的表格

单元格不支持换行，长文本直接截断。改用 Canvas + Frame 自己画。

### D3. 自己画表格：每行一个独立 Frame 会导致列宽不一致

**现象**：中文列看起来"居中"（其实是每行列宽不同）。

**修法**：所有行放进**同一个 grid**，用 `columnconfigure(weight=…)` 共享列宽；表头也放进同一网格，否则永远差几像素。

### D4. 预览面板的尺寸缓存要跟着图变

**现象**：双击能打开新图，面板还显示旧图。

**修法**：换图时清缓存，展开时强制重绘。

### D5. 拖动分隔条会抖成筛子

**修法**：

```
拖动中：完全不重绘，日志停自动滚动，日志 wrap 临时设为 none
松手后：延迟 200ms 重绘一次
尺寸变化 < 14px：直接跳过
```

实测：连续拖 15 次，只重绘 1 次。

### D6. `ttk.Panedwindow` 不能设 minsize

表现是右栏被内容撑住，只能往一个方向拖。换成经典 `tk.PanedWindow`（支持 `minsize`）才能双向压缩。

### D7. 焦点白框

`Treeview` 和只读 `Combobox` 获得焦点时会画白框。`takefocus=0` + 样式层覆盖。

### D8. 周期性刷新会覆盖界面状态

**现象**：截图/测试时把模型名改成中性值，几秒后自己变回去。

**原因**：每 8 秒一次的服务检查会重新拉取模型列表并写回变量。测试时要先关掉 `periodic_check`。

## E. 测试与数据安全

### E1. 自动化测试会写坏用户配置

跑一次测试，用户的目录、尺寸、种子全被改掉。

**修法**：所有配置写入走同一个出口，并加测试开关：

```python
def save_cfg(self):
    if getattr(self, "_no_save_cfg", False):
        return
    ...
```

### E2. 测试产物会污染工作目录

临时输出目录要在测试结束时清掉，否则用户看到一堆 `_demo`、`_ab_test`。

### E3. 长时间自动化测试会占住会话

一次真机等待 20 分钟，体验极差。**能拆成小步就拆**，单次验证控制在 1~2 分钟。

### E4. 改代码后必须确认运行中的实例已重启

改了 `app.py` 但界面没变，八成是旧进程还活着。重启前先按进程名过滤，避免留下多个实例。

## F. 与人协作（给 AI 助手的提醒）

- 说"没问题"之前必须真跑一遍；上一次我没跑就说没问题，结果是 `NameError`。
- 用户说"慢"时，先要**分段耗时**（准备 / 推理 / 补全），不要猜。
- 用户说"没效果"时，先确认**他跑的是不是最新版本**（D8、E4）。
- 清理任何文件前，先列出清单让用户确认，并留可还原的备份目录。
